В третьей главе рассматривается практическая реализация разработанного программного комплекса. Основное внимание уделено устройству вычислительного ядра, серверному слою, клиентскому приложению и экспериментальному анализу полученных результатов. Поскольку именно эта глава связывает математический аппарат с реальным исходным кодом, в ней приведены характерные листинги и пояснения к ним.

\subsection{Реализация вычислительного ядра на Go}

Основная часть алгоритмов сосредоточена в пакете \texttt{compute}. Его центральным элементом является тип \texttt{AdaptiveSparseGrid}, инкапсулирующий параметры области, тип базиса, размерности входа и выхода, а также контейнеры для хранения узлов и входных точек. Выбор Go в качестве языка реализации вычислительного ядра обусловлен несколькими причинами: наличием встроенной поддержки конкурентных вычислений, удобной моделью работы с функциями высшего порядка, предсказуемой производительностью и простотой интеграции в сетевой сервис.

Конструктор сетки выполняет валидацию входных данных, определяет размерность образа функции, вычисляет значения в контрольных точках и затем запускает процедуру построения. С точки зрения программной реализации важно, что вычислительное ядро принимает пользовательскую функцию как аргумент. Благодаря этому один и тот же код используется и для интерполяции аналитических отображений, и для операторов перехода, получаемых численным интегрированием.

В листинге \ref{lst:new_grid} показан фрагмент конструктора, задающего общий сценарий создания сетки.

\begin{lstlisting}[language=Go, caption={Создание адаптивной разреженной сетки}, label={lst:new_grid}]
func NewAdaptiveSparseGridWithContext(
    ctx context.Context,
    funcEval func(Point) (Point, error),
    min, max Point,
    epsilon ScalarType,
    anchorPoints []Point,
    basisType BasisType,
    buildType BuildType,
    maxLevel int64,
    maxNodesInGrid int64,
) (*AdaptiveSparseGrid, error) {
    inDim := int64(len(min))
    if int64(len(max)) != inDim {
        return nil, fmt.Errorf("min and max must have the same dimension")
    }

    sampleOut, err := funcEval(min)
    if err != nil {
        return nil, err
    }
    outDim := int64(len(sampleOut))

    grid := &AdaptiveSparseGrid{
        min:       min,
        max:       max,
        basisType: basisType,
        inDim:     inDim,
        outDim:    outDim,
        nodes:     make(map[string]node),
    }

    anchors, err := grid.calculateOriginalFunctionAtPoints(funcEval, anchorPoints)
    if err != nil {
        return nil, err
    }

    err = grid.build(ctx, funcEval, epsilon, anchors, buildType, maxLevel, maxNodesInGrid)
    if err != nil {
        return nil, err
    }

    return grid, nil
}
\end{lstlisting}

В данном фрагменте видны основные архитектурные свойства реализации: независимость от природы исходной функции, автоматическое определение размерности результата и отделение подготовки данных от собственно построения сетки.

\subsection{Представление точек и векторных значений}

Важной особенностью проекта является то, что интерполируемое отображение может быть как скалярным, так и векторным. Поэтому базовый тип \texttt{Point} реализован как срез вещественных чисел. Над ним определены основные векторные операции. Такое решение позволяет единообразно использовать один и тот же код для одномерных функций, двумерных отображений и численного решения систем дифференциальных уравнений.

В листинге \ref{lst:point_ops} приведены операции над типом \texttt{Point}, которые активно используются при вычислении коэффициентов избытка и оценке ошибок.

\begin{lstlisting}[language=Go, caption={Операции над векторным типом Point}, label={lst:point_ops}]
type Point []ScalarType

func (p Point) Add(other Point) {
    for i := range p {
        p[i] += other[i]
    }
}

func (p Point) Sub(other Point) {
    for i := range p {
        p[i] -= other[i]
    }
}

func (p Point) MulScalar(s ScalarType) {
    for i := range p {
        p[i] *= s
    }
}

func (p Point) Length() ScalarType {
    var sum ScalarType
    for _, v := range p {
        sum += v * v
    }
    return math.Sqrt(sum)
}
\end{lstlisting}

Несмотря на простоту, этот набор методов играет ключевую роль. В частности, норма вектора используется как численная мера значимости коэффициента избытка, а покоординатные операции необходимы для формирования интерполянта в пространстве значений.

\subsection{Ключи узлов и кодирование положения в сетке}

Каждый узел сетки идентифицируется не абсолютными координатами, а набором уровней и индексов. Это позволяет однозначно определять положение узла в иерархической структуре и быстро находить потомков. Для хранения узлов в отображении используется тип \texttt{gridKey}. Его строковое представление формируется бинарной упаковкой целочисленных массивов.

В листинге \ref{lst:grid_key} показан соответствующий код.

\begin{lstlisting}[language=Go, caption={Представление ключа узла сетки}, label={lst:grid_key}]
type gridKey struct {
    level []int64
    index []int64
}

func (k gridKey) String() string {
    totalLength := (len(k.level) + len(k.index)) * 8
    result := make([]byte, totalLength)

    pos := 0
    for _, v := range k.level {
        binary.LittleEndian.PutUint64(result[pos:], uint64(v))
        pos += 8
    }
    for _, v := range k.index {
        binary.LittleEndian.PutUint64(result[pos:], uint64(v))
        pos += 8
    }

    return unsafe.String(&result[0], len(result))
}
\end{lstlisting}

Достоинство такого решения состоит в том, что поиск узла по его положению выполняется за амортизированное константное время. Это особенно важно при рекурсивной интерполяции и при добавлении дочерних узлов во время построения.

\subsection{Реализация базисных функций}

Математическая модель из первой главы непосредственно отражается в коде вычисления одномерного базиса. В зависимости от уровня, индекса и выбранного типа базиса вычисляется значение локальной функции влияния. Именно здесь в реализации различаются линейный и квадратичный варианты.

В листинге \ref{lst:eval1d} показана функция вычисления одномерного базиса.

\begin{lstlisting}[language=Go, caption={Вычисление одномерной базисной функции}, label={lst:eval1d}]
func eval1d(x float64, level int64, index int64, basisType BasisType) float64 {
    if level == 0 {
        if index == 0 {
            return 1.0 - x
        }
        if index == 1 {
            return x
        }
        return 0.0
    }

    h := 1.0 / float64(int64(1)<<level)
    center := float64(index) * h
    dist := math.Abs(x - center)

    if dist >= h {
        return 0.0
    }

    t := dist / h
    switch basisType {
    case BasisTypeLinear:
        return 1.0 - t
    case BasisTypeQuadratic:
        return 1.0 - t*t
    }
    return 0.0
}
\end{lstlisting}

Программная реализация полностью соответствует математической постановке. Для внутренних уровней значение функции зависит только от относительного расстояния до центра узла. Это делает код компактным, а изменение типа базиса сводит к выбору одной формулы в конструкции \texttt{switch}.

\subsection{Построение входных точек и запуск локальных задач}

Алгоритм построения сетки начинается с формирования начальных конфигураций уровней и индексов. Для каждой такой конфигурации запускается построение локальной сетки. На этом этапе появляется возможность параллельной обработки независимых задач.

В листинге \ref{lst:build_parallel} приведён фрагмент функции \texttt{build}, показывающий выбор между последовательным и параллельным режимами.

\begin{lstlisting}[language=Go, caption={Параллельный запуск локальных задач построения}, label={lst:build_parallel}]
if buildType == BuildTypeParallel {
    wg.Add(1)
    go func(k gridKey) {
        defer wg.Done()
        res := g.buildGridTask(ctx, funcEval, epsilon, anchors, k, i, maxLevel, maxNodesInGrid)
        mu.Lock()
        results = append(results, res)
        mu.Unlock()
    }(currentKey)
} else {
    res := g.buildGridTask(ctx, funcEval, epsilon, anchors, currentKey, i, maxLevel, maxNodesInGrid)
    results = append(results, res)
}
\end{lstlisting}

Здесь видно, что каждая стартовая конфигурация обрабатывается независимо. Это оправдано математически: локальные сетки строятся для различных входных точек и не зависят друг от друга до момента объединения результатов. В результате многопоточная обработка хорошо согласуется с логикой метода.

\subsection{Создание узла и вычисление коэффициента избытка}

Одним из центральных этапов алгоритма является создание нового узла. Именно здесь вычисляется точное значение исходной функции, интерполированное значение на уже построенной части сетки и затем коэффициент избытка как их разность.

В листинге \ref{lst:create_node} показан соответствующий фрагмент кода.

\begin{lstlisting}[language=Go, caption={Формирование узла и вычисление коэффициента избытка}, label={lst:create_node}]
func (g *AdaptiveSparseGrid) createNode(
    funcEval func(Point) (Point, error),
    key gridKey,
    entryPoint *node,
    dimension int64,
    additionalNodes map[string]node,
) (*gridKey, error) {
    if _, exists := additionalNodes[key.String()]; exists {
        return nil, nil
    }

    n := node{
        key:        key,
        centerUnit: make(Point, g.inDim),
    }
    for i := int64(0); i < g.inDim; i++ {
        n.centerUnit[i] = getCoord(key.level[i], key.index[i])
    }

    realArg := g.toReal(n.centerUnit)
    etalon, err := funcEval(realArg)
    if err != nil {
        return nil, err
    }

    interp := g.evaluateForDimAndEntryPoint(n.centerUnit, dimension, entryPoint, additionalNodes)
    etalon.Sub(interp)
    n.alpha = etalon
    additionalNodes[key.String()] = n

    return &key, nil
}
\end{lstlisting}

Этот фрагмент хорошо иллюстрирует иерархическую природу метода. Коэффициент \texttt{alpha} не равен просто значению функции; он представляет собой именно недостающую часть информации относительно уже имеющегося интерполянта. Тем самым код напрямую реализует математическое определение коэффициента избытка.

\subsection{Адаптивное продолжение и роль контрольных точек}

После вычисления коэффициента избытка алгоритм решает, продолжать ли уточнение. В качестве первичного критерия используется норма вектора \texttt{alpha}. Однако при малом значении этой нормы возможна ситуация, когда функция имеет сложное внутреннее поведение, не выявленное в центре узла. Для предотвращения такого сценария используются контрольные точки.

В реализации каждый узел проверяет, попадают ли заданные anchor points в его область влияния. Если в такой точке ошибка интерполяции превышает порог $\varepsilon$, уточнение продолжается. Это особенно важно для осциллирующих функций и симметричных зависимостей. По сути, контрольные точки выполняют роль внешней информации, подсказывающей алгоритму, какие области пространства состояний нельзя считать уже достаточно аппроксимированными.

\subsection{Рекурсивная интерполяция по построенной сетке}

После завершения построения объект \texttt{AdaptiveSparseGrid} используется для быстрого вычисления приближённых значений. Интерполяция организована как рекурсивный обход дерева узлов: сначала учитывается вклад текущего узла, затем --- вклад релевантных потомков.

В листинге \ref{lst:evaluate_recursive} показан характерный фрагмент рекурсивного вычисления.

\begin{lstlisting}[language=Go, caption={Рекурсивное вычисление интерполянта}, label={lst:evaluate_recursive}]
func (g *AdaptiveSparseGrid) evaluateRecursive(
    x Point,
    n node,
    processedNodes map[string]struct{},
    additionalNodes map[string]node,
) Point {
    if _, exists := processedNodes[n.key.String()]; exists {
        return make(Point, g.outDim)
    }

    processedNodes[n.key.String()] = struct{}{}
    basis := evalBasis(x, n.key.level, n.key.index, g.basisType, g.inDim)

    if math.Abs(basis) < 1e-9 {
        return make(Point, g.outDim)
    }

    value := n.alpha.Clone()
    value.MulScalar(basis)

    if n.hasChildren {
        for i := int64(0); i < g.inDim; i++ {
            if n.key.level[i] != 0 {
                child, exists := g.getChildForDimAndArg(n, x, i, additionalNodes)
                if exists {
                    value.Add(g.evaluateRecursive(x, child, processedNodes, additionalNodes))
                }
            }
        }
    }
    return value
}
\end{lstlisting}

Программный смысл этого кода совпадает с теоретической формулой суммы иерархических вкладов. Дополнительная оптимизация состоит в том, что если значение базиса практически нулевое, рекурсия по данной ветви немедленно прекращается.

\subsection{Композиция операторов и метод следующей итерации}

Одной из наиболее интересных возможностей разработанной библиотеки является поддержка последовательного применения аппроксимированных отображений. Метод \texttt{MakeNextIteration} использует текущую сетку как оператор, который сначала вычисляет приближённый образ точки, а затем передаёт его следующей пользовательской функции. В результате можно строить композиции вида
\begin{equation}
    F_k = F \circ F \circ \dots \circ F,
\end{equation}
или поэтапно моделировать эволюцию динамической системы на нескольких временных интервалах.

Этот механизм оказался особенно полезным для задач, связанных с дифференциальными уравнениями. Вместо повторного интегрирования на длинном интервале можно интерполировать одношаговый оператор и затем многократно применять его через последовательные итерации.

\subsection{Серверный слой: преобразование формул в вычислимые отображения}

В пакете \texttt{internal/server} реализована логика преобразования пользовательских выражений в функции, пригодные для передачи в вычислительное ядро. Объект \texttt{Formula} хранит скомпилированные выражения для двух компонент, параметр шага и признак режима решения дифференциальных уравнений.

Если пользователь выбирает режим обычной функции, сервер просто вычисляет два выражения в точке $(x,y)$. Если же активирован режим \texttt{DIFFUR}, сервер интерпретирует выражения как правые части системы и численно интегрирует её на заданном временном интервале. Таким образом, одна и та же структура \texttt{Formula.Evaluate} порождает единый интерфейс \texttt{func(Point) (Point, error)}, который затем передаётся в \texttt{compute.NewAdaptiveSparseGridWithContext}.

Практически это означает, что математическое ядро отделено от деталей численного интегратора и от синтаксиса пользовательских выражений. Такая декомпозиция упрощает и сопровождение, и расширение системы.

\subsection{Интегрирование дифференциальных уравнений}

Для вычисления отображений, соответствующих решениям систем дифференциальных уравнений, в сервере реализован адаптивный метод Рунге--Кутты--Фельберга. В коде вычисляются коэффициенты схемы Cash--Karp, после чего оценивается локальная ошибка и автоматически подбирается следующий шаг интегрирования.

Важность этого решения состоит в том, что качество аппроксимации разреженной сеткой напрямую зависит от качества «эталонного» значения функции в узлах. Если бы интегратор был грубым, это вносило бы дополнительную численную ошибку ещё до этапа интерполяции. Применение адаптивной схемы повышает устойчивость результата и делает сравнение различных параметров сетки более корректным.

\subsection{Клиентская реализация и визуальный анализ}

Клиентская часть на Flutter реализует удобный интерфейс эксперимента. Пользователь задаёт формулы, границы прямоугольной области, точность, шаг интегрирования, максимальную глубину узлов и ограничение на размер сетки. Затем клиент отправляет запрос по gRPC и отображает полученный результат.

С точки зрения программной реализации полезно отметить, что клиент содержит собственную модель \texttt{Grid2D}, повторяющую структуру данных сервера. Это позволяет не только отображать узлы, но и локально вычислять значение интерполянта для выбранных точек. Тем самым визуализация не сводится к статической картинке: клиент обладает собственной упрощённой исполнительной моделью построенной сетки.

\subsection{Тестирование корректности}

Корректность вычислительного ядра проверяется набором модульных тестов и примеров использования. В тестах рассматриваются как простые аналитические функции, так и задачи интерполяции решений дифференциальных уравнений. Проверяются следующие сценарии:
\begin{enumerate}
    \item одномерная интерполяция функции $f(x)=x^2$;
    \item многомерная интерполяция функции $f(x,y)=xy+\sin x$;
    \item аппроксимация решения дифференциального уравнения $x'=-x$;
    \item влияние контрольных точек на качество аппроксимации функции $\sin x$;
    \item корректность обработки ошибок размерности и выхода точки за границы;
    \item композиция отображений через метод следующей итерации.
\end{enumerate}

Содержательно эти тесты показывают, что библиотека проверяется не только на уровне отдельных процедур, но и на уровне типичных пользовательских сценариев.

\subsection{Бенчмаркинг и анализ производительности}

В проекте предусмотрены отдельные бенчмарки, позволяющие исследовать влияние размерности задачи, типа базиса, режима сборки и способа моделирования дифференциальных уравнений на время построения сетки. Из структуры тестов можно выделить несколько важных направлений анализа.

Во-первых, измеряется рост стоимости построения при переходе от одномерных к многомерным функциям. Это позволяет количественно оценить влияние размерности на объём вычислений и фактически демонстрирует, в каких границах метод сохраняет практическую применимость.

Во-вторых, сравниваются последовательный и параллельный режимы построения при одинаковых параметрах задачи. Такое сравнение важно для основной темы диплома, поскольку позволяет оценить реальную эффективность конкурентного запуска независимых локальных задач.

В-третьих, исследуются два подхода к работе с дифференциальными уравнениями: прямое включение времени как дополнительной размерности и последовательное применение одношагового оператора через \texttt{MakeNextIteration}. Сравнение этих двух подходов позволяет сделать вывод о том, какой из них лучше соответствует архитектуре разреженных сеток для длительной эволюции системы.

\subsection{Анализ полученных результатов}

Анализ структуры исходного кода, тестов и бенчмарков позволяет сделать несколько выводов.

Во-первых, разработанное вычислительное ядро действительно является универсальным: одна и та же инфраструктура используется для аппроксимации обычных функций, операторов перехода и последовательных композиций отображений. Это существенно повышает практическую ценность реализации.

Во-вторых, выбранная архитектура хорошо подходит для параллельного выполнения. Независимость стартовых конфигураций входных точек позволяет эффективно распараллеливать начальный этап построения без усложнения математической модели. При этом реализация остаётся компактной и понятной.

В-третьих, использование квадратичного базиса оправдано в задачах визуализации и гладкой аппроксимации. Даже без прямых численных таблиц в тексте кода видно, что архитектура тестов и примеров ориентирована на анализ плавных отображений и решений дифференциальных уравнений, где квадратичная форма базиса даёт более естественное поведение интерполянта.

В-четвёртых, проект демонстрирует хороший баланс между исследовательским и прикладным аспектами. С одной стороны, в нём реализован нетривиальный численный метод с адаптивным уточнением и поддержкой параллелизма. С другой стороны, результат оформлен как завершённый программный комплекс с сетевым интерфейсом, наблюдаемостью и клиентской визуализацией.

\subsection{Инструкция по получению графиков и изображений}

Для включения в отчёт содержательных иллюстраций целесообразно использовать как автоматические графики производительности, так и скриншоты интерфейса визуализации. Ниже приведён рекомендуемый порядок действий.

\textbf{1. Подготовка вычислительного окружения.}

Необходимо запустить серверное приложение и клиент визуализации. Сервер поднимается из точки входа \texttt{cmd/diplom/main.go}, клиент --- из каталога \texttt{app}. При необходимости можно использовать docker-compose из каталога \texttt{deploy/docker-compose} для запуска сопутствующих сервисов мониторинга.

\textbf{2. Получение графиков производительности.}

Для построения графиков времени выполнения нужно запустить бенчмарки пакета \texttt{compute}. На практике удобно выполнить тесты командой вида:
\begin{lstlisting}[language=bash, caption={Запуск бенчмарков вычислительного ядра}, label={lst:bench_run}]
go test ./compute -bench . -benchmem > bench.txt
\end{lstlisting}

Полученный файл можно обработать внешним скриптом на Python, через электронные таблицы или средствами Jupyter Notebook. Для отчёта обычно строятся следующие графики:
\begin{enumerate}
    \item зависимость времени построения от размерности задачи;
    \item сравнение последовательного и параллельного режимов;
    \item сравнение линейного и квадратичного базисов;
    \item сравнение двух подходов к работе с дифференциальными уравнениями.
\end{enumerate}

По оси абсцисс рекомендуется откладывать параметры задачи (например, размерность или время интегрирования), а по оси ординат --- среднее время выполнения в миллисекундах. Для наглядности полезно строить графики в одинаковом масштабе для сравниваемых серий.

\textbf{3. Получение изображений структуры сетки.}

Для построения иллюстраций адаптивной сетки нужно запустить клиент Flutter, задать характерную тестовую систему и выполнить вычисление. После отображения результата можно сделать снимок экрана с картой узлов и областью, где видна неоднородность детализации. Наиболее показательны примеры, в которых сетка сгущается около особенностей траектории или в областях быстрого изменения поля.

\textbf{4. Получение скриншотов мониторинга.}

Если требуется показать эксплуатационные свойства решения, можно открыть метрики Prometheus и построить графики времени ответа, размера ответа и числа узлов в зависимости от параметров запроса. Такие изображения хорошо дополняют раздел анализа производительности.

\textbf{5. Подготовка изображений к вставке в отчёт.}

Все готовые изображения следует сохранить в каталог \texttt{Text/img}. Для удобства именования лучше использовать осмысленные имена, например \texttt{parallel_build.png}, \texttt{basis_compare.png}, \texttt{ui_example.png}, \texttt{prometheus_latency.png}. Желательно сохранять изображения в формате PNG с достаточным разрешением, чтобы текст на графиках читался при печати.

\textbf{6. Вставка графиков и изображений в LaTeX-отчёт.}

Для добавления рисунка в текст нужно использовать окружение \texttt{figure}. Пример вставки приведён в листинге \ref{lst:latex_figure}.

\begin{lstlisting}[language={[LaTeX]TeX}, caption={Пример вставки изображения в отчёт}, label={lst:latex_figure}]
\begin{figure}[H]
    \centering
    \includegraphics[width=0.9\textwidth]{img/parallel_build.png}
    \caption{Сравнение последовательного и параллельного построения сетки}
    \label{fig:parallel_build}
\end{figure}
\end{lstlisting}

После этого на рисунок можно ссылаться из текста командой \texttt{\textbackslash ref\{fig:parallel\_build\}}. Для нескольких однотипных графиков рекомендуется выдерживать единый стиль подписей: сначала указывать, что именно сравнивается, затем --- условия эксперимента.

\textbf{7. Практические рекомендации по оформлению.}

При подготовке иллюстраций для отчёта следует придерживаться следующих правил:
\begin{enumerate}
    \item на графиках обязательно подписывать оси и единицы измерения;
    \item использовать единый стиль легенд и цветов для всех сравнительных диаграмм;
    \item не перегружать один рисунок слишком большим числом серий;
    \item для скриншотов интерфейса выбирать только информативные фрагменты, без лишних элементов рабочего окружения;
    \item перед вставкой в отчёт проверять, что изображение читаемо в чёрно-белой печати или без сильной потери контраста.
\end{enumerate}
